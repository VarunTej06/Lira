# Azure playground: rebuild the Liraspaces rehearsal

What this folder does: after you sign in to a **new** KodeKloud Azure playground session, `Setup-Playground.ps1` recreates what we built by hand on 19 Nov 2026: container registry, Key Vault, PostgreSQL, a Blob Storage account for ticket attachments, the database tables, the API and web container apps, and the Let's Encrypt proxy for `test.liraspaces.com`.

Nothing here holds a password. Passwords are generated by the script and kept only in Key Vault.

## Order of work

Sign in first (PowerShell): `az login` with the playground account. Then, from this folder, run one step at a time, or `-Step all`.

| Step | What it creates or does | Time |
|---|---|---|
| `.\Setup-Playground.ps1 -Step check` | Shows the account, the resource providers and the resource group the sandbox gave you | 1 min |
| `-Step infra` | Container registry (admin user on), Key Vault with two generated passwords, PostgreSQL 16, firewall rules, a storage account (Standard LRS, no public access) with a private `attachments` container and its key in Key Vault (`storage-key`) | about 10 min |
| `-Step database` | The `lira_app` role and the tables from `api/migrations`; add `-RunTests` to run the 304 API tests against the real database | 2 min |
| `-Step google -GoogleClientId <id>` | Optional. Keeps the Google OAuth client secret (from the `GOOGLE_CLIENT_SECRET` variable) and a new encryption key in Key Vault, so the API can make Meet links and send emails. Then run `-Step deploy` again. See `docs/03-sop/google-setup.md` | 1 min |
| `-Step mail -MailFrom <address>` | Optional. Keeps the Azure Communication Services Email connection string (from the `MAIL_CONNECTION_STRING` variable) in Key Vault and the sender address in the state, so the API can send confirm-your-email and password-reset mail. Create the Communication Services and Email resources, with an Azure-managed or your own verified domain, in the portal first (`docs/03-sop/email-setup.md`). Then run `-Step deploy` again | 1 min |
| `-Step isolation` | The nine tenant-isolation checks (`docs/03-sop/rehearsal-isolation-test.sql`), run through Docker in WSL | 1 min |
| `-Step images` | Builds the web and API Docker images in WSL and pushes them to the registry | 5 to 10 min |
| `-Step deploy` | Container Apps environment, the API (internal only) and the web app (public) | 5 min |
| `-Step edge` | Caddy in a container, for the Let's Encrypt certificate; prints the DNS record to add | 2 min |
| `-Step status` | Calls `/health`, `/ready`, `/`, `/login` and `/api/me` (must answer **401**) on both addresses | 1 min |
| `-Step all` | `check`, `infra`, `database`, `images`, `deploy`, `edge` in order | about 30 min |

Every step can be run again: names are kept in `.state.json`, existing resources are reused, and the Key Vault passwords are only created when missing.

**The one manual part, in Hostinger:** when `edge` finishes it prints a CNAME for `test` (delete any older `test` CNAME first), TTL 303. Caddy waits 10 minutes before asking Let's Encrypt, so there is time. Check with `nslookup -type=CNAME test.liraspaces.com horizon.dns-parking.com`, then `-Step status`.

**Then try it:** open `https://test.liraspaces.com/signup`, create an account with a password you type yourself, and log in at `/login`.

**Needs:** Azure CLI, Node 22, PowerShell 5.1 or newer, Ubuntu on WSL with Docker (used by `images` and `isolation`), and Hostinger access.

**Tested on 19 Nov 2026 by hand, not end to end by this script.** The script was written after the session closed, so run it step by step the first time and read each message.

## What the sandbox refuses (found on 19 Nov 2026)

| Thing | What happens | What the script does |
|---|---|---|
| New resource group | `AuthorizationFailed` | Uses the one the sandbox gives |
| `az acr build`, `containerapp up --source` | `scheduleRun` denied | Build with Docker in WSL and push |
| Container Apps environment | Name must be `container-app-env`; Log Analytics workspace denied | That name, `--logs-destination none` |
| Container app replicas | Min 0 or 1, max 0 to 2 | 0/2 for web, 1/2 for the API |
| Any certificate (managed or uploaded) | `RequestDisallowedByPolicy` | Caddy gets a Let's Encrypt certificate itself |
| Key Vault | Standard tier, 7-day soft delete, purge protection cannot be switched off | Those settings |
| PostgreSQL | Not in `eastus`; needs Burstable B1ms or B2s, 32 GB, P4 tier, no HA, no zone, 7-day backup, no geo backup, no autogrow | `centralus` and those settings; no `--high-availability` option on this CLI |
| Storage account | **Not yet tried in the sandbox.** Expected to be allowed with the cheapest SKU (Standard LRS). If it is refused, read the policy text and change that one setting | Standard LRS, StorageV2, Hot, public blob access off, TLS 1.2, HTTPS only |
| Container Instances | Needs `--sku Standard`, 0.25 to 2 CPU, 0.5 to 4 GB; Docker Hub pulls can fail | `--sku Standard`; Caddy is copied into your registry first |

If a policy text differs next time, read its **Reasons** line and change that one setting.

## Deploying a new version

Give each new build its own tag: `-Step build -WebTag g2 -ApiTag g2`, then `-Step images` and `-Step deploy` with the same two options. **A redeploy with the tag that is already running does nothing**: Azure only starts a new revision when something in the app's definition changes, and the same tag counts as the same image. If the site still behaves like the old version, this is the first thing to check (the API's `/api/auth/providers` answering 404 means an old API). Apply new database migrations with `-Step database` before deploying a version that needs them.

## Known limits of this rehearsal

- Public database firewall rule for your IP and for Azure services. The real subscription uses a private endpoint.
- Registry admin password for pulls. The real subscription uses a managed identity.
- The proxy count in front of the API (`-ProxyHops`, default 3) must match reality, or the per-address lock reads the wrong address. Call the API and look at the audit table's `source_ip`.
- The storage key sits in Key Vault and, later, in the API as a secret. The real subscription uses a managed identity, no key.
- The storage account allows browsers from the site address only (CORS), and the script sets the list again on each run.
- The Caddy certificate is stored only inside its container. If the container restarts, Caddy asks Let's Encrypt again.

## How the pieces connect, and how to troubleshoot from the cloud side

```
browser --https--> Caddy (container, Let's Encrypt certificate, public IP)
                    --https--> web container app (nginx, public ingress)
                                 /api/*  --http--> API container app (NestJS, internal ingress only)
                                                     --TLS--> PostgreSQL (public endpoint, firewall)
```

Three proxies stand in front of the API (Caddy, the web app's ingress, nginx), which is why `-ProxyHops` is 3. The API is never reachable from the internet: only nginx can call it, by its name `liraspaces-api` inside the environment.

Set these once in PowerShell, with the names from `.state.json`: `$rg`, `$web = "https://<web address>"`.

| Symptom | Likely cause | Check |
|---|---|---|
| The page does not load at all | Caddy not running, DNS wrong, or the web app scaled to zero (the first request takes several seconds) | `nslookup -type=CNAME test.liraspaces.com horizon.dns-parking.com`; `az container show -g $rg -n lira-edge --query instanceView.state`; call the web address directly: `curl -i $web/health` |
| Certificate error on `test.liraspaces.com` | Caddy has not got its certificate yet (it waits 10 minutes, then asks) or DNS did not point at it when it asked | `az container logs -g $rg -n lira-edge` (look for `certificate obtained` or an ACME error); if it gave up, `-Step edge` again |
| `/health` works but `/api/me` gives **502** or **504** | nginx cannot reach the API: it is not running, has no replica, or `API_UPSTREAM` is wrong | `az containerapp show -n liraspaces-api -g $rg --query properties.runningStatus`; `az containerapp show -n liraspaces-web -g $rg --query "properties.template.containers[0].env"`; the value must be `liraspaces-api` |
| `/api/me` gives **404** with an HTML page | The web image is the old one, without the `/api/` forwarding | `az containerapp show -n liraspaces-web -g $rg --query "properties.template.containers[0].image"`; push and deploy the new tag |
| `/api/me` gives **401** JSON | Working: nobody is signed in | |
| Sign-up or log-in gives **403** "did not come from Liraspaces" | The browser's origin is not in `ALLOWED_ORIGINS` (a different address, or http instead of https) | `az containerapp show -n liraspaces-api -g $rg --query "properties.template.containers[0].env"`; add the exact `https://host` and redeploy |
| **500** "Something went wrong" | The API cannot reach or use the database | `az containerapp logs show -n liraspaces-api -g $rg --tail 50` (an error kind and code such as `ECONNREFUSED` or `28P01`); `$web/api/auth/login` is not needed, `curl` the API through nginx only |
| `/ready` on the API is down | The database does not answer: firewall, wrong password, server stopped | `az postgres flexible-server firewall-rule list -g $rg --name <server>` (the rule for 0.0.0.0 must exist); `az postgres flexible-server show ... --query state` |
| Sign-up works but you are signed out at once | The cookie is not kept: `COOKIE_SECURE=true` on a plain-http address, or the browser blocks it | Use the https address; browser developer tools, Application, Cookies, `lira_session` |
| Everybody gets "Too many wrong attempts" | The API reads one shared address for everyone (wrong `TRUST_PROXY_HOPS`) | Query `audit_log.source_ip`: if every row has the same internal address, change the hops and redeploy |
| The new code does not appear | A new revision did not start, or the old tag is still used | `az containerapp revision list -n liraspaces-web -g $rg -o table`; use a new image tag each time |

Useful commands:

```
az containerapp logs show -n liraspaces-api -g $rg --tail 50           # recent console output (JSON lines)
az containerapp logs show -n liraspaces-web -g $rg --follow            # live
az containerapp revision list -n liraspaces-api -g $rg -o table        # which version runs, and is it healthy
az containerapp exec -n liraspaces-web -g $rg --command sh             # a shell inside the container
az container logs -g $rg -n lira-edge                                   # Caddy
curl -i https://<web>/health ; curl -i https://<web>/api/me             # what the outside sees
```

Inside the web container, `wget -qO- http://liraspaces-api/health` tests the internal path to the API directly. If that works but `/api/me` through nginx does not, the problem is in `nginx.conf`.

Log history is not kept in this sandbox (no Log Analytics), so read the logs while you reproduce the problem. The API writes one JSON line per request with a request id (`X-Request-Id` is also sent back to the browser), and never the body, a password or a token.

## Clean up before the session ends

1. **Hostinger:** delete the CNAME `test` and, if you added them, the TXT `asuid.test`. A CNAME pointing at a deleted Azure name can be claimed by someone else.
2. The sandbox removes the Azure resources itself.
